# 极致低功耗模式

> **一句话**：把「访客每次点击都可能触发 25 次 PHP 执行 + 21 次出站」，
> 改造成「访客点击只读一个静态文件；只有内容真的变了、或图片真的第一次被要时，
> 才起一次进程 —— 而那一次永远是幂等的、有上限的、有兜底的。」

VodHub 1.3.0 起默认启用。目标是在 **1 GB / 5 GB 磁盘、2 TB 月流量** 这类
免费虚拟主机上，让配额基本感知不到本站的存在 —— **同时一个功能都不砍**。

---

## 为什么要这么设计

免费主机的配额里，**磁盘是唯一决定性的容量配额**，而 2 TB 月流量意味着
「带宽」几乎出局（本项目典型用量约 24 GB，只占 1.17%）。所以资源优化的重心
全部在 **磁盘、EP、CPU** 三条上。

更关键的是：**磁盘满不会表现为「变慢」，而是逐层崩坏** ——

```
图片落盘失败 → 页面缓存写不进 → 接口缓存写不进（每次访问重新出站）
→ SQLite 写失败（白屏） → 会话文件写不进（登录态失效）
```

所以本模式里所有「上限」和「GC」都不是性能优化，是**生存必需**。

---

## 四层隔离

```
第 4 层：浏览器缓存 / 边缘      CSS、JS、图片 30 天缓存 → 0 请求到达源站
第 3 层：Apache 静态直出        c/<时间桶>/*.html、static/imgcache/*  → 0 个 PHP 进程
第 2 层：PHP 快速读盘           rewrite 不可用 / 每小时首次访问 → 1 个进程 × 约 3 ms
第 1 层：出站与重活             上游刷新、图片首拉、字段富化 → 稳态不发生
```

**核心原则：第 1 层的成本不能由「访客的每一次点击」承担。**

## 六个支柱与对应文件

| # | 支柱 | 落在哪些文件 |
|---|---|---|
| 一 | **页面静态化** | `includes/pagecache.php`、`includes/template.php`（`renderTemplate()`）、`.htaccess` 重写段 |
| 二 | **图片代理本地化** | `includes/imgcache.php`、`includes/functions.php`（`coverUrl()`）、`img.php` |
| 三 | **富化内联** | `play.php`、`templates/*/play.php`、`templates/default/partials/vod_{meta,side}.php`、`static/app.js` |
| 四 | **访客路径零阻塞** | `includes/client.php`（超时 / 负缓存 / 有界刷新 / 搜索不落盘 / `getTypesLocal()`） |
| 五 | **热路径微秒化** | `includes/db.php`（`dbInit` 短路、WAL）、`includes/auth.php`（`sessionRelease()`）、`includes/guard.php`（生产 ini） |
| 六 | **护栏** | `includes/guard.php`（水位、GC、限流）、`robots.txt`、`.user.ini` |

## 后台怎么配

### 1. 容量档位（站点与维护 → 容量档位）

| 档位 | 页面缓存 | 图片缓存 | 接口缓存 | 归一化表 | 合计 |
|---|---|---|---|---|---|
| **紧凑（1 GB 空间）** | 300 个 / **共 15 MB**，保留 2 桶 | 60 MB（约 600 张） | 600 个 / 30 MB | 15 天 | **≈ 162 MB** |
| **标准（5 GB 及以上）** | 1,000 个 / **共 40 MB**，保留 2 桶 | 200 MB（约 2,000 张） | 2,000 个 / 100 MB | 30 天 | **≈ 417 MB** |
| 自动探测 | 按 `disk_total_space()` 判定，≤1.5 GB 视为紧凑 | | | | |

> **页面缓存的「共 15 MB」这个数字，1.3.13 起才真的有代码管着。**
>
> 此前它的实现是一段死代码：`guardGcFiles($dir, PHP_INT_MAX, $maxBytes)`
> —— 而 `c/` 底下全是时间桶目录，没有一个条目能通过 `is_file()`，
> 于是判定恒为「未超限」，**那个总闸从未生效过**。
 * 1.3.11 把它删了，并把本表改成「每桶上限 × 桶数」——
 *   **那是把问题写进了文档，不是解决问题**（代码允许到 15 × 2 = 30 MB）。
 * 1.3.13 真正做成总量闸（`page_total_bytes`）：超限时
 *   **按 mtime 从最旧的桶开始删整个桶**，且**绝不删本小时的桶**
 *   —— 里面的页面正被 `.htaccess` 直出，删了等于把访客正在看的页面变成回源渲染。
 *
> 为什么按「整个桶」删而不是逐文件削：桶是天然的整体单位，
> 逐文件 `unlink` 不会减少目录项、也不真正回收 inode。

> **归一化表那一列也是 1.3.12 才真的生效的。**
> `enrich_days`（15 / 30 天）从 1.3.0 起就写在代码里，
> 但**从未被任何地方读取** —— 那道护栏一直是假的，`enrich` 表也没有任何自动清理。
> 按 100 源 × 每天 200 部新片 × 30 天估算，不清理能涨到约 300 MB
> （1 GB 盘的 30%）。1.3.12 接上了 `guardGcEnrich()`（时间闸 + 行数硬顶）。

> ⚠️ **磁盘 ≤1 GB 请手动选「紧凑」。**
> 不少主机（cPanel 系常见）的 `disk_total_space()` 返回的是**整台服务器的磁盘**
> 而不是你的账户配额，自动探测会误判成大空间。
> 误判的后果有限（两档预算都远小于 1 GB），但紧凑档更稳妥。

### 2. 磁盘水位（自动，无需配置）

```
可用 > 30%  → 正常档
可用 15~30% → 上限 ×0.6
可用 8~15%  → 上限 ×0.5
可用 < 8%   → 保护模式：停止写入页面与图片缓存，后台红字提示
```

**8% 是硬红线** —— SQLite 接近满盘会报 `disk is full`，会话文件写不进去
会让所有登录态失效。进入保护模式后站点**降速但不停摆**：
页面走 PHP 渲染、图片走 `img.php` 转发，功能全部正常。

后台「极致低功耗状态」会实时显示当前百分比与档位。

### 3. 访问密码与页面静态化（互斥，自动）

> **安全红线**：`.htaccess` 直出会**完全绕过 `requireAccess()`**，
> 而 `.htaccess` 无法验证会话是否真的鉴权通过（伪造一个 cookie 就能绕过）。

因此 **`访问密码` 开启 ⇒ 页面静态化自动停用**（`pcEnabled()` 既不读也不写，
`c/` 下没有文件，重写的 `-f` 自然不成立）。后台状态栏会标注
「已开启访问密码 → 按安全要求自动停用」，不需要你记住这件事。

此时全部页面走第 2 层，**仍然要过鉴权**，仍是 1 个进程 × 约 3 ms ——
依然远好于优化前的 7～21 个并发进程。**其余五个支柱全部继续生效。**

### 4. 什么时候该点「清理」

后台「系统缓存」里新增了两项：

- **页面静态缓存**：改了模板 / 样式 / 站点设置却**没看到变化**时勾上。
  （正常情况下任意**配置**写入都会自动全量作废，这里只是手动兜底。）

  > **1.3.11 更正**：这句话此前写的是「任意**配置**写入」，
  > 而「数据源与分组的增 / 改 / 删 / 启停」走的是数据层的裸 CRUD 函数、
  > **从不经过 setSetting()**，所以那一半从来不会自动作废 ——
  > 表现为后台提示「✅ 已更新数据源」、前台一整点内都还是旧页面。
  > 现已改为在 `includes/db.php` 的数据层收口（新增源、改源、删源、
  > 增/改/删分组，以及启停源与图片域名白名单这三条裸 SQL），
  > **凡写 `sources` / `groups` 两张表就必然作废**，并由
  > `tests/test_contracts.php` 第 1 条契约强制，不靠记性。

- **图片本地缓存**：封面需要强制从上游重新取时勾上。
  清掉只是「每张图再付一次 EP」，**功能永不缺失**。

## 已知边界（不藏）

| 边界 | 说明 |
|---|---|
| **静态粒度最细 1 小时** | Apache 的 `%{TIME}` 不支持取模、`RewriteMap` 在 `.htaccess` 中不可用。列表页内容最多滞后 **1 小时 + 一次有界刷新**。**这是时间延迟，不是功能缺失** —— 搜索永远实时（不静态化），翻页与点开播放立刻是新 URL |
| **服务器时区特殊时可能不命中** | 写入时已覆盖「应用时区 / 主机 ini 时区 / UTC」及小时补零两种写法。若三者皆非，`.htaccess` **不会读到错误内容，只是永远回源**，由第 2 层兜底（1 个进程 × 3 ms）。想确认是否命中：看 `.htaccess` 重写后第二次访问是否明显变快 |
| **图片本地化不减月流量** | 省的是 **EP 与出站到上游的请求**。月流量只看「发给访客的字节」，走 `img.php` 还是走 `static/imgcache/` 是一样的。2 TB 带宽下这不重要（占 1.17%），但要知道 |
| **没有实现图片转 WebP** | 落盘时压缩能把 600 张扩到约 2,000 张（省磁盘不是省流量），但图片经过你手时做有损转换有把图画坏的风险，1.3.0 未实现 |
| **没有实现图片分批加载** | `loading="lazy"` 已把首屏并发压到 6～10 张；图片本地化后「一次性爆发」只发生在每张图一生一次。为这点收益承担「JS 失效时图片全不显示」的风险不划算 |
| **禁出站的空间上整体不可用** | 本项目全部数据来自上游，禁出站 = 完全跑不起来。**这是选型问题，不是优化问题**，部署前务必先探针测一下 |
| **WAL 会多出两个文件** | `data.db-wal` / `data.db-shm`。**面板备份时要连它们一起拷**，否则会丢最近写入。不支持 WAL 的主机自动退回默认模式（不报错） |

## 怎么验证它真的生效

### 快速三条

```bash
# 1) 第二次访问同一个列表页，应该明显变快（Apache 直出，0 个 PHP 进程）
curl -o /dev/null -w "%{time_total}s\n" "https://你的域名/list.php?source=1&type=2&page=1"
curl -o /dev/null -w "%{time_total}s\n" "https://你的域名/list.php?source=1&type=2&page=1"

# 2) 静态文件是否在生成
find c -name '*.html' | wc -l

# 3) 图片是否已本地化：同一列表页第二次打开，Network 里不应再有 img.php
du -sh static/imgcache
```

### 后台指标

「极致低功耗状态」里应看到：

- 磁盘可用 **> 8%**（否则会进保护模式）
- 页面静态缓存有文件、页面静态化**已启用**
- 体积都在本档上限内

### 面板指标（连续观察 7 天）

| 指标 | 期望 |
|---|---|
| Entry Processes 峰值 | 从优化前的 7～21 降到 **0～1** |
| 503 / 504 次数 | **0** |
| 磁盘占用 | 1 GB 档 **≤ 15%**、5 GB 档 **≤ 10%** |
| `runtime/cache` 文件数 | ≤ 本档上限，且**连续搜索 500 个不同词后不增长** |
| 月流量 | ≤ 50 GB（2 TB 的 2.5%） |

### 两条硬验收

1. **改配置后前台立即生效**：后台改一次主题色 → 刷新前台 → 必须立刻看到变化。
   不通过说明「配置变更 → 静态缓存作废」这条链有漏洞。
2. **访问密码开启后静态文件不可绕过**：开启访问密码 → 用 `curl` 直接请求
   `https://你的域名/c/<桶>/list-1-2-1.html` → **必须拿不到内容**。
   不通过就是安全洞。

## 排查

| 症状 | 原因 | 处理 |
|---|---|---|
| 页面结构对但**改配置没反应** | 静态缓存没作废 | 后台勾「页面静态缓存」清理；正常情况下写配置会自动清，若复现请提 Issue |
| 封面**莫名其妙长期全裂** | 故障响应被缓存 | `img.php` 已对 4xx/5xx 加 `no-store`；确认上传的是 1.3.0 的 `img.php`；再勾一次「图片本地缓存」 |
| 第二次访问**没有变快** | rewrite 没命中 | 看 `c/` 里有没有文件。有 → 时区对不上，第 2 层兜底仍生效；没有 → 确认 `AllowOverride` 是否允许 `FileInfo`/`All` |
| 磁盘水位一直显示**保护模式** | 真的快满了 | 后台勾「图片本地缓存 + 页面静态缓存」清理；确认档位选对 |
| 后台状态栏**报错或不显示** | 缺少 `config-io.php` 的函数 | 确认上传完整（`includes/` 下 11 个文件都要在） |

更多症状见 [故障排查](troubleshooting.md)。
